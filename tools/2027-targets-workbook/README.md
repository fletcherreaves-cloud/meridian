# 2027 Restaurant Targets Workbook (offline tool)

Generates two Excel workbooks for the owner's 2027 annual-targets process: one real metric per
store (27 stores: 20 OK/MCDOK + 7 FL/Emerald Arches), built from real pulled Meridian/Supabase/
QSRSoft-export data. This is a **standalone offline tool** — it is not a Meridian app feature,
writes nothing to Supabase, and isn't wired into the live app in any way. It exists so this
workbook can be regenerated by a future Claude Code session (or run by hand) without starting the
sourcing work over from scratch.

The companion Claude Doc is "2027 Restaurant Targets Methodology"
(https://claude.ai/artifact/9NMjDv1kXK4Ayyd11Yrabd) — read that first for the full rationale
behind the modeling choices below. This README covers only how to run and extend the tool.

## What it produces

- **`Restaurant_Annual_Targets_Workbook_RESTRUCTURED.xlsx`** (`build.py`) — one tab per metric
  category (OEPE Peak, KVS Peak, R2P Peak, Park Peak, Healthy Peak, Peaks Combined, Service Total
  Day, Sales & Traffic, Labor, CSAT, Digital, Turnover), plus a Read Me and a cross-sheet-linked
  Summary tab.
- **`Restaurant_Annual_Targets_Workbook_ORIGINAL_LAYOUT.xlsx`** (`build_b.py`) — the same metrics
  and math, laid out as a single "Table 1" sheet with several color-coded groups side by side,
  matching the owner's real original workbook's own convention.
- **`Restaurant_Annual_Targets_Workbook_PER_LOCATION.xlsx`** (`build_location_sheets.py`) — one
  tab per store (27 + a Read Me), every metric as its own row instead of its own column, grouped
  by category (same groupings as `ORIGINAL_LAYOUT`'s "Table 1"). Built for a real target-change
  conversation with one store's own GM/supervisor: each row carries 2026 Target (Original), 2026
  Actual, Trend, a district-median peer-context column, the Stretch Applied, a live 2027 Proposed
  Target formula, and three blank columns for an actual decision (Requested By / Reason for
  Request / Your Requested Target) instead of a bare override with no record of who asked or why.
  A summary line atop each store's tab counts how many of its real-2026-target metrics are already
  at/ahead of target vs. behind. Same source data as the other two workbooks (reuses `build.py`'s
  shared setup via `exec()`, same pattern `build_b.py` already uses) — no separate data pull.

All three are `.gitignore`d here (`Restaurant_Annual_Targets_Workbook_*.xlsx`) — they're generated
output, not source, and shouldn't be committed.

Each metric is 7 columns, left to right: **2026 Target (Original) → 2026 Actual → Trend → Adj.
Applied (edit me) → 2027 Target (Proposed) → 2027 Target -- Your Override**, plus a hidden
"Last Year / Ref." column. 2026 Target is pulled from the owner's real original upload where one
exists there (`n/a` where it doesn't — see `_TARGET_2026_COLMAP` in `build.py` for exactly which
metrics have one and why the rest don't). Trend and the Adjustment default are both derived from
each store's own real recent-vs-prior movement, never a flat guess. 2027 Target is a live formula
off 2026 Actual and the Adjustment cell; Override is blank and never recalculates anything else —
it's a second place to write down a different number, not a substitute wired into other formulas.

## Running it

```bash
# PIL/image support (for the circular org logo badges) only has a working compiled _imaging
# extension under python3.13 in a standard sandbox -- 3.11/3.12 PIL installs are broken there.
# If your environment's default python3 already has working PIL, that's fine too; just prove it
# first (import PIL.Image) rather than assume.
python3.13 build.py                    # -> Restaurant_Annual_Targets_Workbook_RESTRUCTURED.xlsx
python3.13 build_b.py                  # -> Restaurant_Annual_Targets_Workbook_ORIGINAL_LAYOUT.xlsx (reuses build.py's setup via exec())
python3.13 build_location_sheets.py    # -> Restaurant_Annual_Targets_Workbook_PER_LOCATION.xlsx (reuses build.py's setup via exec())
```

openpyxl writes formulas as strings with no cached values — **recalculate both files in
LibreOffice headless before using them**, or every formula reads back as blank to pandas/anything
else reading cached values. This needs LibreOffice installed (`brew install --cask libreoffice`
on Mac, or the installer from libreoffice.org on Windows/Linux) — not a Claude-specific tool,
just the free office suite, for its `soffice` CLI:

```bash
soffice --headless --convert-to xlsx:"Calc MS Excel 2007 XML" --outdir . Restaurant_Annual_Targets_Workbook_RESTRUCTURED.xlsx
```

(A Claude Code session re-running this script has an internal recalc helper with better
error-counting than the bare `soffice` command above -- that's a sandbox-only tool, not something
to go install separately; running this yourself outside Claude, the `soffice` command above is
the complete, correct path.)

Both scripts are path-portable (`SCRIPT_DIR`/`DATA_DIR` resolve relative to the script's own
location) — they run correctly from any checkout, not just the sandbox session that first built
them.

## `data/` — what's in here and how to refresh it

Everything in `data/` is either (a) the owner's real original targets upload, used as-is, or (b)
an already-aggregated/derived JSON extract built from a **point-in-time pull** of real data
(Supabase + a batch of owner-supplied QSRSoft/SMG-VOICE/McDelivery exports, pulled 2026-11-23).
None of it is live — re-running the scripts today reproduces the **same** 2026-11-23 numbers.
To refresh with new data, the JSON files below need to be regenerated from a fresh pull/upload,
not just re-run as-is.

| File | Real source | Covers |
|---|---|---|
| `2027_Restaurant_Targets_Original_Upload.xlsx` | Owner's real original 2026/2027 targets workbook upload | The literal 2026 Target values `build.py` reads per store/metric (`_TARGET_2026_COLMAP`) |
| `master-data.json`, `ytd-data.json`, `ytd-files-data.json`, `gap-fill-data.json`, `smart-trend-data.json` | Supabase `qsr_daily_activity_rollup` (OEPE/KVS/R2P/Park/Healthy, Sales, GC, Act vs Sched/Needed) | Speed/Service, Sales & Traffic, Labor basis metrics |
| `roster-current.json`, `hours-per-day.json` | QSRSoft Roster_Statistics export | People headcount targets, labor hours/day basis |
| `turnover-ly.json` | Supabase `turnover_monthly` | Turnover TTM/3mo, prior-year baseline |
| `osat-top2-fix.json`, `fullscale-report-fix.json` | SMG VOICE `FullScale_Report.xlsx` ("Data Only" sheet) | VOICE OSAT Top-2-Box, VOICE Execute As Designed |
| `trendreport-b2b-full-fix.json` | SMG VOICE `TrendReport_YYYY_Detailed.xlsx` (both years) | Overall Satisfaction B2B (LY + real monthly trend) |
| `voice-ead-fix.json` | superseded by `fullscale-report-fix.json` for EAD; kept for reference | — |
| `contacts-data.json` | SMG VOICE comment volume (1-800 Contacts proxy) | 1-800 Contacts |
| `digital-gcrd.json`, `uploaded-files-extract.json` | QSRSoft `Digital_App` export | Digital App % of Sales, Digital App GC/R/D |
| `mcdelivery-3po-fix.json` | `MCDelivery_3PO_...xlsx` export, "Restaurant Time"/"CSAT" columns | McDelivery Wait Time, McDelivery Star Rating |
| `mcdelivery-gcrd-combined-fix.json` | `McDelivery_...xlsx` / `GC_-R-D_McDelivery_...xlsx`, "All Vendors" sheet | McDelivery GC/R/D (real total across all 6 vendor/channel streams — see the trap this fixed in `memory/finding-voice-mcdelivery-export-field-mapping-2026-11-23.md`) |
| `lindsay-18213-profile.json`, `lindsay-18213-ytd.json` | Backfill profile for loc 44689 (Lindsay, relocated 2026-11-09, ~8 real days of its own data) from its predecessor 18213 | Every rate metric for 44689 |

See `memory/finding-voice-mcdelivery-export-field-mapping-2026-11-23.md` in the main repo for the
field-mapping traps (ambiguous columns, wrong-polarity guesses caught and fixed) behind the VOICE/
McDelivery files specifically — read that before re-pulling any of those exports.

## Known open items (deliberately left as-is, not bugs)

- **Turnover / staffing forecasting is an open, deferred item (owner, 2026-11-23).** `turnover_ttm`
  is sourced from the original upload's "TTM Shift Leader T/O" column, which may be a different
  cohort (shift leads only, not all crew) from this metric's own definition — flagged in-cell via
  comment, not resolved. `turnover_3mo` has no 2026 Target at all (the file's closest columns,
  "0-90 Day Crew T/O" and "YTD Crew T/O", are each a different real-world measure). The owner may
  end up doing this section manually against McDonald's PDW (People Data Warehouse) data instead —
  don't guess a mapping here without a fresh conversation.
- **McDelivery Wait Time / Star Rating 2026 Target reads `n/a`, not the universal threshold.** The
  original file's values there ("< 3 Minutes", ">4.5") are the identical number for every store,
  not an individualized per-store target (owner-confirmed 2026-11-23) — copying it into every row
  would misrepresent it as one. 2027 Target still proposes a real number off actual results; the
  owner will set a real per-store number via the Override column after meeting with operators.
- **43701 (Ponce de Leon)** opened mid-2026 — its Sales/GC annualization uses its own real
  operating-day count (`DAYS_ELAPSED_OVERRIDE`), not the district's, so it isn't diluted by days
  before it existed.
- **Tab/header colors are matched directly to the owner's real original upload's own per-category
  fills** (measured, not guessed — see the `SECTION_COLORS` comment in `build.py`).
